# dev3 recovery and replay risks

Read-only review on 2026-10-13 against live `dev3` metadata, extended on 2026-10-14 with active `dmuat` metadata and dry-run transactions. These findings are not proof that the same code is in Production after deployment. A `QUEUED`, `ACCEPTED`, HTTP 201, or queue `COMPLETED` result must be followed through to the relevant downstream state. The [DMUAT recovery workbook](DMUAT-Recovery-Scripts-and-Test-Transactions.xlsx) has the **Dev Guide Coverage** tab for 20 guide scenarios plus the Order Management reference, script text, and read-only test evidence.

## Replay blocks by process

| Process | Live evidence and failure mode | Block replay when | Scriptable boundary |
| --- | --- | --- | --- |
| Quote product configuration | `EQXQuoteAgentProductConfigurator` saves the CPQ instance at lines 269–277 and only then links items and marks success at 281–286. Its catch at 290–296 returns `success=false` without rolling back the prior save. The IBX lookup is optional at 212–215 but `ibxInfo.Id` is dereferenced at 281. | Any prior attempt reached `save-instance`, the result is ambiguous, a QuoteLineItem/product hierarchy already exists, or IBX/catalog/required attributes are missing. Retrying the whole action may add duplicate root and child lines. | Read-only snapshot of Quote, QuoteLineItems, attributes, product/pricebook, context and prior execution evidence. A replay wrapper must refuse an existing matching line graph and require a known pre-save failure. Repair post-save linking as its own operation. |
| Quote status, approval and booking | `EQXQuoteStatusChangeHandler` publishes only on an eligible status **change** (lines 36–49). `QuoteStatusChangeHandler` then may sync a primary Quote and also creates booking rows (45–81). | A no-op status update is proposed as a retry, or a status toggle would change approval/acceptance state or fan out to other subscribers. | Read-only inspection of exact Quote status/history, approval state, event/log receipt and latest booking queue. A narrowly scoped booking replay can be considered only after confirming the upstream Quote state is final and there is no active job. |
| Portal create order | `PlaceOrderHeaderFirstService` returns HTTP 201 and the Order ID before enqueuing line processing (31–43). The async phase forces line operations to `POST` on the existing header (123–139) and runs post-processing afterwards (162–239). `PlaceOrderAsyncProcessor` retries exceptions up to three times (43–68). The nominal `PlaceOrderAsyncReplayService` has no live method; its old replay methods are commented out (248–250). | The Order already has any created line, post-processing effect, pending/processing async job, or unknown prior attempt outcome; the original complete request payload is unavailable; the error is a data/configuration failure. Full create/add-lines replay may duplicate work. | Read-only timeline by exact Order ID, request reference, line reference, AsyncApexJob and post-processing logs. A purpose-built script can prepare a candidate plan and refuse to execute when any line/reference collision or active attempt exists. There is currently no callable replay method in `PlaceOrderAsyncReplayService`. |
| Order status and booking | `EQXOrderStatusChangeHandler` emits events on creation-complete transition or allow-listed status transition (102–143). `OrderStatusChangeHandler` creates a booking row and queues processing from each event (30–61). `BookingProcessQueueable` maps `SKIPPED` to queue `COMPLETED` (349–356) and marks unprocessed rows completed (482–499). `OrderStatusRetryQueueable` logs a refresh-price callout error and still updates Order status (70–84). | A booking row/job is active, the source Order/line state is incomplete, a queue says `COMPLETED` but logs show skipped/missing data, or price refresh failed. Never toggle header status just to cause the event. | Read-only queue/log/Opportunity checks. For an isolated failed booking after source data is corrected, create one new `NEW` booking row and queue one processor job with a recorded recovery ID; verify resulting Opportunity values and downstream sync separately. |
| External order placement | `EQXOrderPlacementService` supports a root/product-root/batch-scoped submission (83–94), selects lines outside In Fulfillment/Cancelled/Closed (107–132), and POSTs with `Correlation-Id` set to Order Number (263–276). A callout exception is logged but returns an empty result (298–325). The code does not establish that this header is a server-side dedupe key. | There is an in-flight submission, an earlier external acknowledgement, or a timeout/exception with unknown external outcome for the exact root and batch. Also block if selected lines or attributes are incomplete. | Read-only exact payload, eligible line list, prior request/response and external acknowledgement. Only submit a narrowly scoped root/batch after a human confirms the external system did not accept it. |
| Billing to Oracle OSM | `triggerOracleCloudClass` passes *all* OrderItems to `OracleCloudIntegrationController`, which enqueues one job per supplied item and swallows enqueue exceptions (26–47). `oracleCloudIntegrationProcessOrder` expands supplied roots to child lines (78–81) and calls Oracle (435–440); it treats JSON `status='Success'` as success without checking HTTP code (442–448), and a failure setting `Billing_Triggered__c` is only debugged (450–470). | Any prior Oracle receipt or unknown timeout, an in-flight queueable, a previous `Success` log even if `Billing_Triggered__c` is false, a missing Order/line dependency, or an all-items request that would resend children separately. | Read-only root POF/child hierarchy, current billing fields, job state, Transaction_Log request/response and Oracle receipt. Submit at most one confirmed root POF at a time using the exact Order ID, then verify Oracle and Salesforce independently. Never infer failure solely from a blank billing flag or absent log. |
| Assetization and outbound asset sync | `FulfillmentStepAssetizeRetryBatch` is deliberately limited to `StagedAssetize`, Failed/FatallyFailed, active plan, `UNABLE_TO_LOCK_ROW`, minimum 15-minute age, and 3 attempts in 7 days (lines 40–52, 136–155, 206–256). `EQXStaleAssetOrderRepair.dryRun()` writes a `Transaction_Log__c`; `planFor()` is the read-only preview, while `run()` deletes AssetAction records and changes assets/periods. `AssetIntegrationBatch` selects flagged Assets older than 15 minutes and forwards those with blank API response (10–31); `AssetIntegrationService` invokes an external Integration Procedure and logs its response (89–145). | Assetize failure is validation/catalog/data rather than a transient lock; plan is no longer active; step is too fresh or at retry cap; any asset action or outbound response may already exist; source Asset history is unavailable for a stale-asset repair. | The existing retry batch can be run for its *documented lock-error subset* after checking scheduled/running jobs. Stale-asset repair requires an exact eligible Order and inspected `planFor()` preview. Outbound sync needs exact Asset ID plus external acknowledgement check before another send. |

In dev3, `FulfillmentAssetTrigger` is inactive and `FulfillmentAssetUpdate` is the active flag-flip outbound trigger. `AssetTriggerHandler.processedIds` also prevents a second enqueue of the same ID within one transaction. Its queueable-capacity loop silently leaves excess IDs unsubmitted in a large transaction; inspect affected Assets and logs after a bulk update. The one-ID recovery templates avoid that overflow.

## Additional scoped routes and current blockers

- **Quote and Order VDC.** The Quote wrapper dispatches `EQXCallVDCAsyncBatchCls` for one Quote POF; a response may stamp several lines. The Order route in `EQXOrderVDCService` can route Cabinet/Circuit/CPC child lines through a related PC/SC line and delayed jobs. Check the exact request and every related capacity result before a resend. `OrderItem.VDCCheckConfigStatus__c` exists in dev3 Tooling `FieldDefinition` (`OrderItem.00NWI00000RddrZ`), but the connected `dev3` user cannot query it and anonymous Apex cannot reference it statically. This user's assigned profile/permission set is absent from the field's returned `FieldPermissions`. The Order VDC template hard-stops if its runtime describe cannot see the field; use an account with verified access and retest the template after deployment. Tooling `ApexClass.IsValid` changed during inspection, so its momentary value is not treated as a release finding.
- **Caplogix.** `CaplogixIntegrationService.sendRequest` and `CaplogixIntegrationServiceOrder.sendRequest` can enqueue callouts for the exact interface key. Capacity reservation/release, CFR, booking, cancellation, and completion can have external business effects. `OrderCFRRequest` can fan out over every required root POF on an Order; it is not a single-root replay. For any interface, confirm the external outcome for that interface and all affected roots. A prior timeout or blank Salesforce log is ambiguous.
- **Order decomposition.** `OrderDecompositionAPI.decomposeOrder(orderId, oneRootPofId)` is a targeted path. The service has checks for an existing fulfillment plan, step sources and lines, but partial work and a second attempt still need inspection. The recovery template refuses an existing POF step source, lists existing fulfillment lines, and prints the per-POF result. Do not run whole-Order decomposition to repair one root POF.
- **Quote to Opportunity line sync.** `QuoteLineItemSyncAsync.syncQuoteLineItems` overwrites mapped OpportunityLineItem custom fields from linked QuoteLineItems. It does not create missing Opportunity lines or repair links. Compare values and mapping direction before the one-Quote replay.
- **Fulfillment activity / possible Jarvis subscriber.** Active `Publish_Fulfillment_Activity` Flow v30 publishes `Publish_Activity__e` from a completed FulfillmentOrderLineItem. No in-org Jarvis class, Flow, Named Credential, or receiver was identified; `PublishActivityTrigger` has its Flow invocation commented out. Salesforce publish acceptance does not establish that the external subscriber received or applied the activity. Do not toggle `Activity_Creation_Completed__c` to retrigger the Flow. A replay built from today's line values can misstate a historical CREATE/UPDATE; compare history or the original payload. The separate CPL activity event handler can create FulfillmentOrder/Line records without a dedupe guard and is not a substitute replay.
- **FulfillmentAsset event.** Active `FulfillmentAssetEventTriggerHandler` publishes `Publish_Asset__e` on the creation-completed transition and also on later updates while completion remains true, regardless of which field changed. That event is separate from the `SyncFulfillAsset_Technical` Integration Procedure. A no-op update can emit another event; use the exact event template only after checking the subscriber receipt and original payload values.

For scripts 22–26, `ActivityNumber__c` and `Activity_Number__c` are distinct API fields despite the same display label; confirm the key used by DSO056. For the guide's exact Customer Accepted case with **no interface message**, none of the 34 matching DMUAT Quotes passed script 09's `Quote_To_Order_inSync__c=false` guard: all 34 were already true. Inspect the scheduled batch and any existing Order; the earlier script 09 preflight used a Quote with an interface error and does not validate this exact case.

All 32 scripts compiled across 73 read-only DMUAT cases: 47 passed preflight or diagnostics, 26 met expected guards, and every run recorded zero DML, callouts, and queueables. No replay branch was exercised. A passing preflight establishes only the observed eligibility checks, not a corrected downstream outcome.

## Cross-cutting preflight and verification

1. Resolve the exact record and branch (Quote revision, Order type, root POF, product SKU, batch, and source channel). Capture linked records, last attempt, timestamps, and error messages before any action.
2. Distinguish a rejected request from a timeout after external acceptance. Query `AsyncApexJob`, booking queue, Transaction Log, Integration Log, FulfillmentStep and downstream receipt as applicable. A missing or failed Salesforce log does not establish that Oracle, placement, Boomi, or Siebel received nothing.
3. Exclude running/queued attempts. Check source data and catalog prerequisites before replay. The September production stuck-order investigation shows a missing Geo Scope attribute led to a failed amendment patch while the header still became Configured; re-running full order creation or toggling status would not repair that line.
4. Generate a dry-run manifest with exact IDs, stage, existing effects, proposed action, and expected end-state. Execute only a single approved stage for a single record/root per run, record job/receipt identifiers, and verify both Salesforce state and external acknowledgement. Stop on an ambiguous outcome.
5. Catalog parity is a release prerequisite, not a retry action. The October 12 Prod–DMUAT comparison found 117 Attribute Definitions, 134 picklist values and 535 classification-attribute associations only in DMUAT; this does not describe dev3, but demonstrates that missing product metadata can make a replay deterministically fail until the deployment is corrected.

No production replay or org mutation was performed in this review.
