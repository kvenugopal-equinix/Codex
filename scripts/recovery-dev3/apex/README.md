# dev3 anonymous Apex recovery templates

Each `.apex` file is a complete anonymous Apex script for one exact recovery scope (some require both a parent ID and one line ID). Copy its **entire raw contents** into Salesforce Inspector's **Apex Execute** or **Apex Runner** screen. The script runs in the Salesforce org where you are already logged in. If your Inspector has only REST Explorer, see the short fallback in the [main Inspector instructions](../README.md#run-a-template-from-salesforce-inspector).

The [DMUAT recovery workbook](../DMUAT-Recovery-Scripts-and-Test-Transactions.xlsx) includes all 32 templates and 73 dry-run transactions, with DMUAT IDs, recorded results, and prefilled Inspector scripts. Its **Dev Guide Coverage** tab maps 20 guide scenarios plus the Order Management reference to the available route and its execution boundary.

Replace the exact 18-character record ID placeholder(s) and any script-specific inputs near the top. The default `dryRun = true` performs read-only preflight queries and writes `RECOVERY PREFLIGHT` to the Apex execution log. Review that output and the existing downstream state. For a script with a live replay path, set `dryRun = false` and its named confirmation flags only after the incident review, then execute once and verify the downstream result before another attempt. Scripts 31 and 32, and script 21 with a technical FulfillmentAsset ID, remain diagnostic only.

`08-assetize-lock-one-step.apex` calls the deployed batch's public `execute(null, oneStepList)` synchronously. Its preflight repeats the eligibility checks from the batch's broad `start()` query; it does not submit the broad batch. Verify `FulfillmentStep.State` and the retry log after it runs. Several templates submit asynchronous jobs or outbound events; acceptance of a job or event is not proof of external completion.

`06-fulfillment-asset-outbound.apex` requires completed local Asset creation and confirmation that any stored API response was inspected and failed. The completion check is a manual recovery boundary; the deployed DMUAT outbound trigger also permits records without that flag. Repair incomplete local creation before using this recovery template.

`14-quote-sync-to-opportunity.apex` calls the deployed one-Quote sync method and verifies `Opportunity.SyncedQuoteId`. `15-order-decomposition-one-pof.apex` passes one root POF to the deployed decomposition API and reports its per-POF result. `16-quote-lines-to-opportunity-products.apex` can overwrite mapped Opportunity product fields and requires complete QLI-to-OLI links plus an explicit overwrite confirmation. `18-fulfillment-asset-event.apex` re-publishes one `Publish_Asset__e` directly; it requires confirmation that the current values match the missing historical event and that the external subscriber has no receipt. These are distinct stages; do not treat completion of one as proof of another.

These snippets were drafted from Apex classes and active flow metadata retrieved from dev3 on 2026-10-13. Recheck those contracts after deployment. The `OpportunityLegacy`, Oracle billing, Asset, and FulfillmentAsset replays require a downstream absence check because Salesforce logs can be incomplete after an external success.

All 32 templates compiled in DMUAT across 73 anonymous Apex dry-run cases (45 on October 13, 28 on October 14): 47 passed preflight or diagnostic checks and 26 stopped at expected guards. Every run recorded zero DML, callouts, and queued jobs. These checks cover deployed references, configuration, and preflight conditions. They do not validate recovery writes, interface business eligibility, external responses, or subscriber delivery. `OrderCFRRequest` had no `Required` root candidate and was rejection-tested only. The workbook includes the exact DMUAT test IDs and results.

The active BMMR, Fiber Connect, and Path provisioning Flows reset the selected FulfillmentOrderLineItem before publishing; generic Cortex staging does so only when `ActivityType__c='Provisioning'`. These resets clear activity and scheduling fields and can change completion, primary, and PONR flags. The scripts print the before/after field plan. Confirm the DSO003 send history and the DSO056/Cortex receipt before replay. `ActivityNumber__c` and `Activity_Number__c` are separate API fields with the same display label; verify which value DSO056 uses. The deployed Path Flow records a Fiber Connect transaction-log class label, so a Path-only log filter can miss prior work.

For [`19-stale-order-header-closure.apex`](19-stale-order-header-closure.apex), the service's own `dryRun()` writes a `Transaction_Log__c`; the script uses `planFor()` for a read-only preview. [`27-approval-outcome-status.apex`](27-approval-outcome-status.apex) previews the selected outcome's direct children and all relevant current-revision peer/future approvals because an approval can advance another sequence. ## VDC, Caplogix, and fulfillment activity

- `10-quote-vdc.apex` submits one root QuoteLineItem through `EQXQuoteVDCService_Wrapper` with interface `VDCAPI`. The script requires `Root_Line__c=true` and a `Product_SKU__c` listed in `Root_Product_SKU__mdt`, matching the payload builder's POF classification. A root-flagged child SKU fails preflight. The batch sends one chosen POF but the response can update several QuoteLineItems. Confirm the external outcome is absent before submission.
- `11-order-vdc.apex` uses `EQXOrderVDCService` with endpoint key `VDCCheckConfig`. Cabinet, Circuit, and CPC lines route through their PC/SC sibling and can re-call VDC for that sibling or stamp multiple response lines. **Current dev3 user is blocked:** Tooling `FieldDefinition` lists `OrderItem.VDCCheckConfigStatus__c`, but the connected user's `sobject describe` omits it and static anonymous Apex cannot query it. The template compiles by checking dynamic describe and requires `orderVdcPathVerified=true` before dispatch. Resolve access/visibility, validate the deployed service end to end, and re-run dry preflight before considering execution.
- `12-caplogix-quote.apex` submits one Quote to the selected reviewed Caplogix interface. `CFRRequest` requires one root QuoteLineItem; the other interfaces build a Quote hierarchy. The live metadata keys reviewed are `CheckCapacity`, `MACDCheckCapacity`, `ReserveCapacity`, `ReleaseCapacity`, `CFRRequest`, and `CLXQuoteStatusUpdate`. The template requires both an external absence confirmation and a full hierarchy review. `MultiReservation` is deliberately excluded: its current response branch does not add changed QuoteLineItems to its update list, so replay would not reliably repair local state.
- `13-caplogix-order.apex` submits one Order to the selected reviewed interface. `OrderCFRRequest` sends a separate callout for every root line with `CFR_Status__c='Required'`; the other interfaces build an Order hierarchy. It requires explicit confirmation for every root or the full hierarchy. Order Caplogix automatically retries transient HTTP 408, 429, and 5xx responses, so a timeout can have an unknown external outcome.
- `17-fulfillment-activity-event.apex` reconstructs one `Publish_Activity__e` payload from the active `Publish_Fulfillment_Activity` Flow v30. Choose the missing `CREATE` or `UPDATE` event explicitly; `UPDATE` requires its original `changedFields__c` JSON. This uses current line values, so confirm they match the missing historical event using history or the original payload. The event consumer is external and its identity as Jarvis has not been verified in dev3. Confirm that consumer has no successful receipt before publishing. Do not toggle activity fields to cause a record-triggered replay.

The original 18 templates compiled in dev3 with placeholder IDs, which stop at the ID guard before any write. A read-only `CREATE` preflight for `17-fulfillment-activity-event.apex` against one existing dev3 activity completed with zero DML, zero callouts, and zero queued jobs. Successful `EventBus.publish` or a submitted async job is only acceptance by Salesforce; verify the external consumer's acknowledgement separately.
